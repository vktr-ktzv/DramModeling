# Архитектура решения

Краткое описание того, из чего собраны модели DRAM-контроллера (SystemC / TLM-2.0),
как они связаны и как в них течёт время. Детали сборки и запуска — в `README.md`,
история работ — в `SPIKE_PLAN.md`.

## 1. Состав

Единственный исполняемый файл — `spike_dram`: co-simulation, в которой
RISC-V-ядро Spike встроено внутрь SystemC-хоста, а обращения гостя к DRAM идут
через DRAM-контроллер и отдельную модель микросхемы `DramChip`. Контроллер
(`dram_controller_base.cpp` + `dram_controller_async.cpp` +
`dram_controller_sync.cpp`) от источника запросов не зависит: очереди и арбитраж
общие, различается только `serve()`-модель. Банки, строки, тайминги и трасса
живут в `DramChip` (`dram_chip.cpp`).

## 2. Ядро контроллера

```
        b_transport(trans, delay)
 initiator ───────────────►  ┌──────────────────────────────────────┐
 (StoreBuffer)           2   │ DramControllerBase                   │
      ──────────────────────►│  read_queue_ / write_queue_          │
       порт 0: чтения,        │  next_request()  (round-robin)       │
       порт 1: записи         │  finish_request() ──► счётчики       │
                              └───────────────┬──────────────────────┘
                                              │ serve()  (SC_THREAD)
                                              │  issue() -> mem_socket->b_transport
                                              ▼
                                      ┌──────────────────────────────┐
                                      │ DramChip                     │
                                      │  banks[state, open_row]      │
                                      │  FSM ACT/RD/WR/PRE, trace    │
                                      └──────────────────────────────┘
```

- **`DramStorage`** (`include/dram_common.h`) — линейный массив байт (`std::vector`)
  и единственное место, где данные реально читаются/пишутся (`access()`).
  Владеет им `DramChip`; контроллер данные не трогает.
- **`DramControllerBase`** — общая часть. Держит `kPorts = 2` tagged target-сокета,
  на каждом регистрирует `b_transport`, плюс `mem_socket` (initiator) к `DramChip`.
  Очереди `read_queue_`/`write_queue_` хранят `Request{trans, done}`. Число
  `conflicts_` растёт, когда в момент выбора готовы **обе** очереди.
  `turnaround()`/`remember()` хранят последнее направление, чтобы смена
  чтение↔запись стоила штраф.
- **`DramControllerAsync`** — `serve()` берёт задержку доступа из `DramChip`
  (`issue()` → `DramChip::b_transport`), добавляя только `switch_penalty` (20 нс).
- **`DramControllerSync`** — тот же `serve()`, но синхронизирован по
  `clk.posedge_event()`, а штраф смены направления кратен периоду
  (`cycles(n) = clock_period_ * n`). Банковая модель настроена с
  `quantum = clock_period`, поэтому её задержки уже кратны такту.

`serve()` — единственный «двигатель» времени в модели: он снимает запрос из
очереди, получает задержку у `DramChip` (та меняет состояние банков и пишет
трассу), ждёт её (и штраф за смену направления) и будит инициатора. Он же даёт
естественный **back-pressure**: инициатор физически не может выдать следующий
запрос, пока не обслужен текущий.

### Модель `DramChip`: банки, FSM, трасса

`DramChip` (`include/dram_chip.h`, `src/dram_chip.cpp`) — отдельный модуль с одним
`simple_target_socket`. Адрес декодируется как `[столбец | банк | строка]`
(по умолчанию 6 бит столбца, 2 бита банка), у каждого банка хранится `state`
(`Idle`/`Active`) и `open_row`. В `b_transport` работает автомат (лекция 6):

```
Idle --ACTIVATE--> Active --READ/WRITE--> Active --PRECHARGE--> Idle
```

- `Idle` — нет открытой строки: `ACTIVATE (+tRCD)`, затем колоночная команда;
- `Active`, та же строка — row hit: только `CAS (+tWR для записи)`;
- `Active`, другая строка — row miss: `PRECHARGE (+tRP)`, `ACTIVATE (+tRCD)`,
  затем колоночная команда.

`DramTiming.quantum` (ноль для async, период такта для sync) округляет каждую
задержку вверх до кратного. Каждая команда кладётся в `trace_`
(`time, command, row_access, type, bank, row, col, latency`) и выгружается в CSV
через `dump_trace()`; счётчики `row_hits/row_misses/activations/precharges`
печатаются в stdout.

### Контракт `b_transport`

`b_transport` **блокирующий**, а не LT-стиль: он кладёт `Request` в очередь,
уведомляет `new_request_`, затем делает `wait(done)` на **локальном** событии,
адрес которого лежит в самом `Request`. Когда `serve()` доходит до этого запроса,
он делает `done.notify()`. К моменту возврата время уже продвинуто, поэтому
выходная `delay` выставляется в `SC_ZERO_TIME`. Благодаря локальному событию на
каждый запрос контроллер корректно работает с несколькими одновременными
инициаторами.

## 3. Co-simulation (`spike_dram_main.cpp`)

```
 RISC-V-гость (Spike)
   ld/st
     │
     ▼
 sim_t → mmu_t → bus_t          (адрес приходит уже смещённым на базу)
     │
     ▼
 SpikeTlmDevice::load/store      (abstract_device_t)
     │
     ▼
 StoreBuffer                     (write-back буфер, см. §5)
   load ─► блокирующее чтение ─────────────┐
   store ─► очередь ─► kWriteLanes ────────┤
                                           ▼
                                   DramControllerBase.socket[0..1]
                                           ▼
                                     DramControllerBase.mem_socket
                                           ▼
                                       DramChip
                                    (банки + трасса)
```

- **`CosimSim : sim_t`** переопределяет виртуальный `idle()`: за вызов делает
  ровно один `processor_t::step(1)` и `wait(cycle)`. То есть SystemC владеет
  планировщиком, а время двигается **на каждой инструкции**.
- **`SpikeRunner : sc_module`** с `SC_THREAD(run)` целиком крутит `sim_t::run()`
  внутри `sc_start()`. Только в контексте SystemC-потока легален `wait()`,
  который использует блокирующий `b_transport`.
- **`SpikeTlmDevice`** превращает `load/store` гостя в TLM-транзакцию. Адрес он
  **не** смещает повторно — `bus_t` уже вычел базу устройства.
- По завершении гостя `SpikeRunner` вызывает `buffer.flush()`, печатает
  статистику и `sc_stop()`.

### Карта памяти

| Диапазон                | Что                                            | Кто обслуживает          |
| ----------------------- | ---------------------------------------------- | ------------------------ |
| `0x4000_0000` (256 МиБ) | MMIO DRAM-контроллера                          | `SpikeTlmDevice` → TLM   |
| `0x8000_0000` (2 ГиБ)   | ОЗУ Spike: код, стек, `tohost`/`fromhost`      | `mem_t` (без контроллера) |

`start_pc = 0x8000_0000`, `dtb_enabled = false`; CLINT/PLIC/triggers не поднимаются.

## 4. Как течёт время

Время **отвязано** от памяти: один такт на инструкцию плюс задержки DRAM.

```
idle(): step(1) → ++insns → wait(cycle)          # cycle = 10 нс
обращение к DRAM: b_transport → очередь → wait(done)
                  serve() → issue() (DramChip: FSM + трасса) → wait(access) → notify
```

Чтения **блокируют** гостевой поток на время обслуживания; задержки DRAM
складываются со временем инструкций. Записи, наоборот, буферизуются и уходят в
контроллер параллельно (см. §5), поэтому они почти не удлиняют критический путь.

Задержка доступа теперь не константа, а результат автомата банков (row hit/miss,
precharge), поэтому суммируется по каждому запросу:

```
T ≈ N_insn * cycle + sum(access_latency_i) + N_turnaround * switch_penalty
```

Для sync `access_latency_i` дополнительно округляется вверх до такта. Пример по
`fib.elf`: async `insns=191, time≈4544 нс` (avg 26.6 нс/доступ), sync
`insns=191, time≈5220 нс` (avg 37.7 нс/доступ); данные и количество обращений
совпадают, различается тайминг. На `write_burst.elf` расходятся уже и счётчики
банков (async `activations=3072`, sync `activations=3527`), то есть и сами трассы.

Есть страховочный лимит `kMaxInsns` (50 млн): при его достижении симуляция
завершается с ненулевым кодом.

## 5. Store buffer: несколько транзакций в полёте

`include/store_buffer.h` / `src/store_buffer.cpp` — write-back буфер между
гостем и контроллером. Его задача — отвязать медленные записи от CPU и допустить
несколько транзакций «в воздухе» одновременно.

- `store()` только копирует данные в `pending_` и сразу возвращается — CPU не
  ждёт DRAM.
- `kWriteLanes = 3` SC_THREAD-дренажа параллельно вынимают записи и отправляют
  их в контроллер (через `write_socket`, порт 1). Пока контроллер обслуживает
  чтение CPU, в его очереди скапливаются записи.
- `load()` делает чтение через контроллер (`read_socket`, порт 0) и форвардит
  ещё не применённые записи — **store-to-load forwarding**. Перекрывающиеся по
  адресу записи не отправляются, пока более ранняя в полёте, поэтому порядок
  записей по адресу сохраняется.
- `flush()` (вызывается перед `sc_stop()`) ждёт, пока очередь опустеет, чтобы
  финальный снимок памяти был полным.

Именно буфер делает так, что в контроллере в один момент могут находиться
несколько транзакций, а значит арбитр видит конфликты чтение/запись. Насколько —
зависит от нагрузки (число конфликтов async / sync):

| Тест                      | async                  | sync                  |
| ------------------------- | ---------------------- | --------------------- |
| `fib` (мало записей)      | 1                      | 1                     |
| `write_pair` (2 записи+чтение) | 1000              | 1000                  |
| `blocked_copy` (блочный memcpy) | 3070              | 4457                  |
| `write_burst` (бенчмарк трасс)  | 0                 | 2232                  |

На `write_burst` расхождение максимально: длинный backlog записей «протекает»
из фазы записи в фазу чтения по-разному в зависимости от скорости обслуживания,
поэтому async и sync приходят к разному порядку команд и разному row hit rate.

## 6. Ключевые инварианты и подводные камни

- **Один `serve()` на контроллер.** Все запросы (любой порт, любое направление)
  сериализуются одним потоком; параллелизм есть только у инициаторов/буфера.
- **`conflicts_`** — не ошибка, а счётчик моментов, когда арбитру пришлось
  выбирать при непустых обеих очередях.
- **Адрес в `SpikeTlmDevice`** уже смещён; повторное вычитание базы — баг.
- **`b_transport` из чужого потока.** Его нельзя звать из цикла Spike напрямую —
  только из `SC_THREAD` внутри `sc_start()`.
- **`DramStorage` и размер.** Диапазон `DramChip` — 256 МиБ; адреса-запросы
  обязаны попадать в него, иначе `TLM_ADDRESS_ERROR`.
- **Один FSM на `DramChip`.** Банки и трасса общие для обоих контроллеров; в
  одном запуске к чипу подключён ровно один контроллер. Разница sync/async — в
  `quantum` и в том, как `serve()` ждёт.
- **SystemC 3.0.2 и C++26.** SystemC и пользовательский код должны собираться
  одним `-std`, иначе получится undefined reference на `sc_api_version_...`.
